## 2. 任务主表字段建议（`biz_task`）

说明：当前 Swagger 已支持 `deptId`、`sceneCode`、`name`、`refType`、`refId`、`executeMode`、`priority`、`planStartTime`、`planEndTime`、`assigneeId`、`remark`。表中标记为“新增”的字段，建议同时补入 `POST /api/v1/biz/task/create`、`POST /api/v1/biz/task/update` 及分页/详情响应。

### 2.1 必须字段：P0 核心字段

| 字段 | 类型示例 | 创建/修改时 | 当前后端 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | bigint / string 返回 | 后端生成 | 现有 | 主键；前端以字符串处理，避免 JavaScript 大整数精度问题。 |
| `taskNo` | varchar(64) | 后端生成 | 现有响应 | 任务编号，建议部门/日期/流水号组合，必须唯一。 |
| `deptId` | bigint | 创建必传或由当前部门推导 | 现有 | **核心隔离字段**。ADMIN 在全局视角创建时应必传。 |
| `sceneCode` | varchar(64) | 创建必填 | 现有 | **核心业务字段**。必须校验为已启用场景编码；建议创建后不允许直接修改。 |
| `name` | varchar(200) | 创建必填、可修改 | 现有 | **核心展示字段**，任务名称。 |
| `taskStatus` | tinyint | 后端默认 `0` | 现有 | **核心流程字段**：`0待执行、1执行中、2待核查、3已失败、4已取消、5已完成`。应由执行、成果、核查流程驱动，不建议普通 update 任意修改。 |
| `priority` | tinyint / int | 创建可传，默认 `0` | 现有 | **核心排序字段**。建议标准化：`0低、1中、2高`。 |
| `executeMode` | varchar(16) | 创建可传，默认 `MANUAL` | 现有 | **核心执行字段**：`MANUAL` / `AUTO`。目前 AUTO 可先预留。 |
| `planStartTime` | datetime | 建议创建必填 | 现有 | 计划开始时间，任务总览按它筛选。 |
| `planEndTime` | datetime | 建议创建必填 | 现有 | 计划结束时间；应校验不早于开始时间。 |
| `refType` | varchar(16) | 可选，默认 `NONE` | 现有 | 关联飞行对象类型：`PLAN`、`TASK`、`NONE`。 |
| `refId` | bigint | 条件必填 | 现有 | 当 `refType` 为 `PLAN`/`TASK` 时必填；为 `NONE` 时应为空。 |
| `assigneeId` | bigint | 建议创建必填 | 现有 | 负责人用户 ID。若允许“待分派任务”，可先为空，但执行前应校验已分配。 |
| `description` | varchar(2000) / text | 建议创建可填、可修改 | **新增** | 面向业务人员的任务说明。不要复用 `remark`：现有 `remark` 仅管理员可见。 |
| `rangeName` | varchar(200) | 有范围时建议必填 | **新增** | 原 Mock 的 `area`，例如“西山林区片区A”；它是范围显示名称，不是实际面积。 |
| `rangeArea` | decimal(18,4) | 后端按 geometry 计算优先 | **新增** | 任务范围面积；建议后端计算并返回，前端不作为可信来源。 |
| `rangeAreaUnit` | varchar(16) | 后端固定或返回 | **新增** | 建议固定 `km2`；异常面积仍可按现有规则使用 `mu`（亩）。 |
| `geometryAvailable` | boolean | 后端维护，只读 | **新增** | 是否存在可展示范围；无范围任务必须返回 `false`。 |
| `geometryFeatureCount` | int | 后端维护，只读 | **新增** | 当前任务范围的 GeoJSON 要素数。 |
| `geometryUpdatedAt` | datetime | 后端维护，只读 | **新增** | 范围最近更新时间。 |
| `rangeThumbnailUrl` | varchar(1000) | 后端维护，只读 | **新增** | 任务范围列表缩略图 URL；由保存 GeoJSON 后的后端生成流程写入。 |
| `coverImageFileId` | bigint | 创建/关联影像时必填 | **新增** | **每个任务必须有至少一张影像**。此字段指向任务影像中的封面文件，供列表直接展示。 |
| `coverImageUrl` | varchar(1000) | 后端根据文件生成，只读 | **新增** | 图斑原图或可访问预览地址；应有权限校验。 |
| `coverImageThumbnailUrl` | varchar(1000) | 后端根据文件生成，只读 | **新增** | 图斑缩略图地址，用于任务总览，避免列表加载大图。 |
| `imageCount` | int | 后端聚合维护，只读 | **新增** | 任务已关联影像数量，必须大于等于 `1`；创建任务可先上传影像再关联，或与创建接口同时提交。 |
| `createBy` | bigint | 后端从登录人取得 | 现有响应 | 创建人 ID，审计字段。 |
| `createTime` / `updateTime` | datetime | 后端维护 | 现有 | 审计字段。 |

**影像落库规则：** 主表只保存封面影像引用和影像数量；多张影像不应塞入一个 JSON 字段。建议以 `biz_task_media` 关联表或现有 UAV 素材表关联记录保存 `bizTaskId`、`mediaId/fileId`、`isCover`、`sort`、`lng`、`lat`、`shootTime` 等信息。任务创建、提交执行或进入“待核查”前，后端应校验至少存在一条有效影像关联；`coverImageFileId` 必须指向其中一条。

**任务范围规则：** 现有 `POST /api/v1/biz/task/geometry/geojson` 仅能读取范围。仍需新增 `POST /api/v1/biz/task/geometry/upsert`，最小请求字段应为 `bizTaskId`、`geometry`（GeoJSON FeatureCollection）、`coordinateSystem`（固定 `EPSG:4326` / WGS84）；可附带 `geometryType`、`rangeName`、`area`、`areaUnit`、`remark`。保存成功后继续通过现有 GeoJSON 接口读取范围。

### 2.2 非必须但建议字段：P1 体验和业务完整性字段

| 字段 | 类型示例 | 建议 | 来源/用途 |
| --- | --- | --- | --- |
| `assigneeName` | varchar(100)，响应冗余/联表返回 | 建议返回，不建议作为主表真值 | Mock 的 `assignee`；列表直接展示负责人姓名。 |
| `deptName` / `sceneName` | varchar，响应冗余/联表返回 | 建议返回，不建议重复存主表 | 列表和详情减少前端二次查询。 |
| `actualStartTime` / `actualEndTime` | datetime | 建议后端状态流转时写入 | 展示实际执行时长，已有响应字段。 |
| `resultRequirements` | JSON 数组或子表 | 建议 | Mock 的 `resultRequirements`，如照片、视频、巡查报告；任务交付要求。 |
| `contactName` | varchar(100) | 可选 | Mock 的 `contact`。若联系人永远是负责人，可由 `assigneeId` 推导，不必重复存储。 |
| `contactPhone` | varchar(32) | 可选，注意脱敏和权限 | Mock 的 `phone`。建议存原始号码，接口按角色脱敏返回。 |
| `remark` | varchar(1000) | 已有 | 内部备注，仅管理员/部门管理员可见。 |
| `rangePreviewUrl` | varchar(1000) | 建议 | 大尺寸任务范围预览图，可用于详情弹窗或导出。 |
| `rangeThumbnailFileId` | bigint | 建议 | 范围缩略图文件 ID，便于鉴权、文件迁移和重新生成。 |
| `images` | 影像对象数组，仅详情接口返回 | 建议 | 不存主表；由 `biz_task_media` 或现有 UAV 素材关联查询返回。每项建议含 `mediaId`、`fileName`、`imageUrl`、`thumbnailUrl`、`originalUrl`、`lng`、`lat`、`shootTime`。 |
| `progressPercent` | int（0-100），只读 | 建议 | 由任务状态、工作流、飞行与成果数据计算；不建议前端手填。 |
| `workflowNodes` | JSON 数组，只读 | 建议 | Mock 的 `workflow`。应由后端根据状态、关联飞行、成果和核查记录计算，不建议作为可编辑主数据。 |
| `statistics` | JSON 对象，只读 | 建议 | Mock 的 `metrics`。飞行次数、飞行时长、巡查面积、异常数、已完成节点数等应由后端聚合计算。 |
