# 高标田工程设施管理专属工作台改造方案（待确认）

> 本文是实施前的产品与前端改造清单，不代表功能已开发或后端接口已具备。依据为本次业务描述和仓库现有工作台实现；没有将参考资料中的描述当作新的用户指令。

## 1. 目标与边界

本场景有两条关联但不能混为一谈的业务线：

1. **设施建档**：已建成高标准农田工程设施上图入库，形成唯一设施档案和二维码。设施可以是点（如泵站、机井、基站）、线（如沟渠、管线、田间道路）或面（如蓄水池、晒场等）。具体设施分类以实际台账为准。
2. **问题处置**：群众或巡检人员扫描某设施二维码，针对该设施上报一次问题；系统生成独立报修任务，完成受理、审核派单、现场核查和维修、部门复核、结案归档。一个设施可关联多次报修，设施编号不等于任务编号。

本次拟建设的是第二条业务线的**专属工作台**，同时在工作台中读取第一条业务线的设施档案和空间位置。不能把设备报修任务当成“异常图斑任务”，也不应要求报修人先画一个图斑。设施本体范围与本次故障影响范围分别存储、分别显示。

## 2. 对现有项目的判断

- 场景路由已有 `farmland-facilities` 映射，但 `src/workspace/config/farmland-facilities.ts` 仍是“设施识别→状态评估→维修下发→复核归档”的旧巡检四节点配置，不符合新流程。
- `src/views/WorkspaceView.vue` 当前以非粮专页或共用通用工作台为主；新场景需要显式分支到自己的工作台，不能只换标题而复用图斑表单。
- 非粮工作台现有的深色流程页头、节点状态、本人节点标记、待办提示、内容区卡片栅格、只读权限提示、附件上传与提交后刷新方式可以作为交互和布局参考；业务字段及图斑对比组件不照搬。
- 现有任务接口有任务详情、`refType/refId`、任务几何、工作流节点 `resultData/files/operateLogs` 等通用能力，但已看到的前端类型里没有可直接确认的“工程设施台账—二维码—报修工单”完整契约。当前“工程设施总览”读取的是已发布设施图层与要素数量；**图层要素不等于已赋码、可扫码的设施实体**。
- 旧场景的实际待办规则应继续遵守：只以真实工作流中本人当前办理节点列为待办，本人已完成节点保留在已办；不根据任务负责人或页面默认节点推断“我”的权限。

## 3. 建议的数据关系和任务入口

建议形成“设施档案 → 扫码报修记录 → 业务任务/工作流 → 维修记录”的关联链：

- 设施档案：稳定的 `facilityId`、设施编码、二维码标识、设施类型、点/线/面几何、所属项目/行政区域/管理单位、建设与管护信息、状态、相关资料。二维码内容建议为可解析到稳定设施 ID 的标识或受控链接，不直接塞入可变的设施名称、联系方式。
- 一次扫码报修：独立的 `reportId` 和 `taskId`，关联同一 `facilityId`；记录报修时间、报修人/联系方式、故障位置与描述、证据、来源（扫码）、地理位置。一码可以产生多次报修，但要提示同一设施是否已有未结案任务，避免重复派单。
- 设备类型为线或面时，扫码仍锁定该设施；报修人可以补充“故障发生点/线段/影响面”。该故障位置与设施完整几何是两个对象。无地理配准的现场照片只能作为照片证据，不能冒充可叠加地图的影像。
- 入口：手机扫码打开设施档案及报修表单；提交成功后建立真实任务。后台【任务列表】仍只看详情，【我的待办】在本人节点到达时提供进入工作台入口，已处理任务继续可回看。扫码入口的登录、匿名上报与验证码/防滥用规则待确认。

## 4. 五节点主流程（拟定）

### ① 任务受理

定位：把扫码上报形成的真实任务呈现给受理人员；核对设施、报修内容，决定受理、退回补充或合并重复报修。若系统把“创建任务”即视为受理完成，则本页可像现有工作台一样作为只读受理记录，不虚构一个办理节点；具体以工作流定义为准。

页面：顶部任务摘要；左侧设施卡片和地图（点定位、线高亮或面高亮），右侧报修描述、问题部位、原始上报材料与受理意见；下方显示设施历次报修和操作时间线。线/面设施应能定位到本次报修的局部位置。

证据：扫码记录/设施编码、报修现场照片为主要材料；可附短视频、语音或文档，但格式和上限由后端规则确定。没有照片时是否允许提交待确认。上传应是真实文件选择与后端保存，上传失败不得显示成功。

### ② 部门审核

定位：核实管辖关系、问题等级和责任单位，形成统一派单。审核结果包括通过并派单、退回补充、转交其他部门、判定重复/无效等；可用结论以真实流程配置为准。

页面：左侧展示设施档案、位置、报修证据和历史工单；右侧为审核意见、问题类别/等级、紧急程度、承办部门/人员、办理期限、派单说明。多人/多部门协同如后端只支持单一下一办理人，界面必须如实限制。

证据：审核说明和派单记录为结构化数据；仅在需要时追加认定附件、补充照片/文档，不强制重复上传报修照片。

### ③ 现场核查

定位：现场人员复扫设施二维码，确认是否为同一设施，核实故障并完成维修处置记录。若核查人和维修人不是同一角色，维修应作为本节点内有独立负责人、期限、状态的子工单，或拆成第六个主节点，不能用一个“已核查”按钮冒充“已维修”。

页面：左侧固定设施地图与故障部位；右侧分“到场核查”“处置/维修”“结果提交”区块。记录故障属实与否、问题等级、影响范围、原因、处理措施、材料/配件、处理时间、现场负责人、恢复运行或测试结果。点设施标点，线设施标故障线段，面设施标故障区域；绘制结果不覆盖设施原始几何。

证据：到场定位/复扫记录、维修前照片、维修过程或关键工序照片、维修后照片、测试/试运行结果；必要时附材料清单、工单签认、视频。若核查后判定无需维修，应填写原因并上传支持材料（具体必填由业务确认）。

### ④ 部门复核

定位：由有复核权限的人员核对维修完成情况、证据充分性和设施状态，给出通过或退回整改。退回后应重开现场处置并保留原核查、维修、复核记录，不覆盖历史。

页面：左侧并排查看报修前/维修后照片与设施地图，右侧为复核清单、抽查方式（现场/材料）、复测结果、复核意见和退回原因。普通照片可并排或卷帘查看；只有具备空间配准的材料才做地图叠加。复核时可定位线段或面状维修范围。

证据：复核现场照片或复测记录、必要的验收单/签认材料；若仅依据材料复核，记录依据和复核人，不伪造“已到场”。

### ⑤ 结案归档

定位：核对完整链路后结案，固化设施本次维修记录并回写设施状态。仅真实完成且通过复核的任务可结案；退回、撤回、无法维修等特殊路径需明确审批规则。

页面：以只读档案为主，汇总设施信息、扫码报修、受理、派单、现场核查和维修、复核、全部附件、操作留痕；提供真实可用的归档/下载入口。归档后二维码查设施时能看到最新状态和历史报修记录，但历史证据不应被后续任务覆盖。

证据：默认复用前序材料，不要求再次上传；如业务需要，可增加结案意见、验收单或签字文件。没有后端档案生成/下载能力时只展示已存材料，不放假“导出成功”按钮。

## 5. 布局与交互要求

- 保留已有工作台的 `header + content` 框架：页头为场景名、任务名、五节点流程、本人办理标记和其他待办入口；内容区随窗口自适应铺满，浏览器缩放 100% 时尽量只让卡片内部滚动，窄窗口再合理降级为整页滚动。
- 页头区分“当前正在查看的节点”和“流程实际所处节点”；已经由本人办完的节点仍标“我”。未到达节点不可通过地址参数强行进入；他人节点可查看但按钮显示“无权限操作”提示。
- 统一顶部反馈小窗、上传进度、保存草稿和提交确认；失败保留已填内容。节点提交后回读后端真实状态再更新流程，不本地猜测流转成功。
- 任务摘要从“图斑数量/异常面积”改为“设施编码/类型/几何类型、故障等级、所属管护单位、受理时间、当前节点/时限”。清楚显示设施状态与工单状态，不用一个状态词混表示。
- 地图沿用现有地图服务体系与主题色，设施点/线/面分别以合适符号高亮；故障部位可编辑但操作需受当前节点权限控制。地图服务加载失败时显示错误和文字坐标/位置描述，不能以假的底图或假位置替代。
- 现场照片可预览、删除（仅本人可编辑时）、查看上传人/时间；移动端拍照/选择文件的体验需覆盖扫码上报。界面图像可用占位图做视觉开发，但验收时真实任务必须显示真实附件，不能把演示图当证据。

## 6. 实施清单（本轮不执行）

1. 核对设施台账、二维码解析、扫码上报、维修子工单、工作流路由、附件及归档接口；确定字段和权限后补充接口类型。沿用现有通用任务/工作流能力，但不强行把设施 ID 塞入现有受限 `refType` 枚举或异常图斑字段。
2. 将 `farmland-facilities` 的场景配置调整为确认后的五节点；在工作台入口显式选择新场景组件，其他场景和现有后端接口调用保持不变。
3. 建设共用设施摘要、设施地图/故障几何、附件区、流程历史区，再分别完成五个业务面板。可复用现有布局与反馈组件，不直接复用非粮的图斑字段、地类判断、无人机复核表单。
4. 接通扫码任务入口、节点权限、待办/已办、真实提交和退回路径；按点、线、面三类设施及多人流转分别验收。
5. 做窗口自适应、权限/空状态/接口异常、文件上传、重复报修和归档回看测试；不通过注入虚构流程数据来展示“已完成”。

## 7. 请先确认的业务决策

1. **维修节点**：五节点主流程是否固定？“现场核查”和“维修施工”若由不同人员负责，是否允许增加独立“维修处置”节点；若不允许，是否已有可分派的维修子工单能力？这是闭环真实性的关键。
2. **设施台账与二维码**：设施唯一 ID/二维码由哪个系统生成？扫码后的报修入口是否允许未登录人员提交？当前发布的工程设施图层能否关联到逐条设施档案？
3. **角色与证据**：受理、审核、核查/维修、复核、归档分别由哪些固定角色/部门办理？各节点哪些照片/记录必须上传，是否需要签字或电子验收单？
4. **空间与重复报修**：点、线、面三类设施的坐标系/几何来源是什么？同一设施已有未结案报修时，是提示继续上报、合并到原单，还是禁止新建？
5. **结案规则**：无法维修、误报、超期、退回重修各走什么路径？结案后设施状态是否自动更新，是否需要生成可下载的完整档案？

以上决策确认后再进入代码修改；尤其不能仅凭当前设施图层与通用任务接口假设二维码扫码、维修派单、归档接口已经可用。
