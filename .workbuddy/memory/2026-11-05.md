## 设施台账「状态改不动」排查（新增/编辑 bizStatus 不生效）

- 现象：新增设施选「异常」→ 列表与统计仍为正常；编辑弹窗改状态也无效；统计 abnormalCount=0。
- 前端链路核查结论：`src/components/FacilityEditDialog.vue:16/40` 已把 `bizStatus` 放进 payload，枚举为 NORMAL/ABNORMAL/CHECKING/DISCARDED；`src/api/facility.ts:47-48` 直接 POST `/v1/biz/facility/add|update`；`src/api/client.ts` 无字段裁剪。
- 列表展示用 `bizStatusName || bizStatus`（`EngineeringFacilityLedger.vue:82`），说明前端对后端返回字段不确定。
- 判断：前端传参正常，问题大概率在后端（add/update 未落 biz_status：DTO 字段缺失、实体映射/默认值覆盖）。待排除项：后端状态若是数字字典码，前端字符串枚举会被静默丢弃。
- 验证方法：DevTools Network 看 add 请求 payload 与响应 data.bizStatus；再看 page 接口单条记录 bizStatus 原始值。
- 【已定论】用户截图 DevTools Payload：`{deptId:1, facilityNo:"", name:"test2", facilityType:"DITCH", bizStatus:"ABNORMAL"}`，code=0 但落库为正常。同一 payload 中 facilityType=DITCH 能正确显示为「沟渠」→ 字符串枚举契约成立，仅 bizStatus 被后端丢弃。结论：后端 bug，前端无需改传参。
- 产出 `docs/facility-bizstatus-not-persisted-issue.md`（含实测 payload、后端 6 项排查点、回归验收标准），可直接发后端同学。

## 操作日志报错的真正原因（前端 int64 预处理 bug）
- 不是后端问题：`src/api/client.ts` 的 `parseJsonWithSafeIntegers` 用正则 `(:\s*)(-?\d{16,})(\s*[,}])` 给长整数加引号，会命中 **JSON 字符串内部** 的 `": 1234567890123456789}"`（如日志 `detailJson` 里存了 int64 ID），插入裸引号破坏转义 → 整个响应 `JSON.parse` 抛 `Expected ',' or '}' after property value`。已用 node 复现同样的报错文本。
- 位置从 131 变 134 只是后端数据内容变了，根因未变。
- 修复：改为字符串感知扫描 `quoteLongIntegers()`（跟踪 inString/转义，仅对独立数字 token 且位数 ≥16 加引号），并加 `LONG_INTEGER_HINT` 快速路径（无长整数直接 JSON.parse）。5 组用例通过（字符串内大整数/顶层大整数/负数/普通数字/转义引号）。
- 影响面：该 transform 作用于所有接口，任何"字符串字段里含长数字文本"的响应都会炸，不只操作日志。
- `vue-tsc` + `vite build` 通过。
