### 追加：百度地图 App 内扫码仍回首页 —— 已定位真因并给出三码方案
- 现象：微信扫码正常进百度地图 H5；**用百度地图 App 的扫一扫**扫码仍落到首页。
- 真因（用 PowerShell `Invoke-WebRequest` 带 `baidumap/20.12.0` UA 实测得到）：
  - 服务器**按 UA 分流**：App UA 请求 `api.map.baidu.com/marker?...` 时，**302 到**
    `https://map.baidu.com/mobile/webapp/place/marker/qt=inf&vt=map&act=read_share&code=276/third_party=uri_api&point=...&title=...&l=17`
  - 其中 `code=276` 是**临时标注码**。该页面本身能渲染（含「到这去」`/mobile/webapp/place/linesearch/...`），但在百度地图 App 内，`map.baidu.com` 是自家域名会被 Native 接管，App 无法把 `code=276` 这类临时码还原成地点 → 回落到首页。
  - 微信/系统相机走的是 Web 渲染（PC/移动 H5 页），所以正常。
- 结论：**一条 https 链接无法同时满足微信与百度地图 App 内扫码**。App 内扫码必须给 `baidumap://` scheme。
- 已实施：弹窗改为 **三张码**
  1. 高德地图（`uri.amap.com/navigation`，微信/相机）
  2. 百度地图（`api.map.baidu.com/marker`，微信/相机，进定位页点「到这去」）
  3. 百度地图 App（`baidumap://map/direction?destination=latlng:<lat>,<lng>|name:<名称>&mode=driving&coord_type=bd09ll&src=webapp.tzscene.nav`，用百度地图 App 扫，直进驾车）
  - scheme 里**只对中文名称做 `encodeURIComponent`**，保留 `latlng:` `,` `|` `name:` 字面结构（百度 scheme 认这个写法）。
  - 弹窗 560 → 640，码 172px（`min(172px,22vw)`），`flex-wrap:wrap` 防窄屏溢出。
- 构建通过（28.30s），产物里三条链接与编码写法均已核对。
- 副产物发现：`api.map.baidu.com/marker` 的移动端页面里，「到这去」指向 `/mobile/webapp/place/linesearch/...&tab=line&routeType=2`，说明百度移动 H5 的路线入口是 `linesearch`，如果以后要找更稳的百度 H5 路线页可以从这里入手。

### 重要纠错：列宽真正生效的位置在 `_tasks.scss`，组件里改是无效的
- 用户反馈「还是没改好」，复查发现前两轮改的 `TaskListsView.vue` 里的 grid **全都不会生效**。
- 原因：`src/styles/system/_tasks.scss` 用 **`#app .task-list-page .task-table-row`** 定义列宽，特异性 `(1,2,0)`（ID 级）> 组件 scoped 的 `(0,3,0)`（类 + `[data-v]`）。组件里那几条 `grid-template-columns` 是历史遗留的死规则。
- 顺带发现：同一选择器在组件里散落 4 处（8 列 / 8 列 / 9 列 / 9 列），列数早已是 9，前三处是老的，极易误导。
- 正确处理：
  1. `_tasks.scss:22` 基础列宽 → `minmax(0,1.1fr) minmax(0,.74fr) 108px 104px minmax(0,.84fr) 94px 84px minmax(190px,2.3fr) 54px`
  2. 断点 `@media(max-width:1450px)` → `...96px 92px...78px minmax(120px,1.8fr) 50px`；`@media(max-width:1150px)` → `...84px 84px...72px minmax(100px,1.4fr) 46px`
  3. 表头不换行：把原来的 `... > span:nth-child(7){white-space:nowrap}` 改成 **`#app .task-list-page .task-table-head > span{white-space:nowrap;overflow:hidden;text-overflow:ellipsis}`**（全列生效，且 ID 级能压过组件里的 `nth-child(4){white-space:normal}`）
  4. 删掉组件里已死的两条 grid 规则，并在 style 开头写明「列宽以 `_tasks.scss` 为准，这里改不生效」，防止再犯。
- 关键经验（通用）：**这个项目里凡是 `#app xxx` 前缀的全局样式都会压过组件 scoped 规则**，调布局/配色时先确认有没有全局覆盖，否则改了看不到效果。
- 校验：`vite build` 28.79s 通过；`index-*.css` 里三条 grid 与通栏表头 nowrap 规则均已确认。

## 新接口：通用内容二维码 `/v1/biz/facility/qrcode/content`
- 定义（线上文档核实）：`POST /api/v1/biz/facility/qrcode/content`，需 `bearerAuth`。
  - body：`{ content: string(≤1000，必填), size: int32(默认 300，120–1000) }`
  - 返回：200 二进制 PNG；错误仍是 BaseRsp JSON（下载类例外惯例），错误码 10809 生成失败。
- 用途：**内容完全由前端给定，服务端不拼接**；官方描述点名典型场景就是「百度地图导航双码」（https 标注码 + `baidumap://` scheme 码）。
- 与现状对比：目前弹窗是在浏览器用 `qrcode` 库 `toDataURL` 生成（4 张码 ≈ 4 次同步调用、零延迟、离线可用）。走接口则每次多一次往返、依赖后端可用性，但能统一尺寸/纠错级别，且可复用到服务端出码场景（消息推送、导出 PDF、印刷）。
- 我们实际内容长度：百度 marker ≈323 字符、百度 scheme ≈208、高德/腾讯更短，均远小于 1000 ✓
- 结论：**弹窗继续用前端生成**更合适；该接口留给服务端出码需求。若日后要切换，改动很小——把 `QRCode.toDataURL(url)` 换成 blob 请求，并复用 `FacilityQrcodeDialog` 里已有的 `readBlobError()` 解析错误体即可。
